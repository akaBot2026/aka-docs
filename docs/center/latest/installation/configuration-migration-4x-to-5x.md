# Configuration Migration from 4.x to 5.x

> This guide lists the configuration updates to review when upgrading **Akabot Center 4.0.0.14** to **5.0.0.0, 5.0.0.1, 5.0.0.2, 5.0.0.4, 5.0.0.5, 5.1.0.0, or 5.1.0.1**. Apply the common changes first, then the settings for your exact target version and enabled features.

For server installation, software prerequisites, and moving data to a new Windows server, follow [Server Migration and Upgrade to 5.x](/docs/center/latest/installation/migrate-server-upgrade-5x.md).

## **1. Prepare the Configuration**

1. Confirm the exact target version. Settings introduced in the 5.0 branch are not necessarily included in the 5.1 branch.
2. Back up the database, license, workflow files, and existing `application.yml`, `application-dev.yml`, and `application-prod.yml`, including external configuration and service options.
3. Use the configuration bundled with the **target V5 package** as the starting point. Merge environment-specific values from V4 rather than replacing the V5 files with complete V4 files.
4. Confirm the active Spring profile in `application.yml` or the service's Java options. Apply production values to the configuration actually loaded by that profile.
5. Preserve the environment's database URL and credentials, broker and Redis connections, service URLs, storage paths, and secret references. A changed sample value is not a requirement to change an existing credential or database engine.

For a WAR deployment, the bundled configuration is under `webapps\ROOT\WEB-INF\classes\config` in the Tomcat directory. If your deployment loads configuration externally, update that configuration as well.

**Note:** You only need to add or override settings when the bundled V5 values do not meet your requirements. The YAML examples below are configuration fragments; merge them into existing sections without duplicating top-level keys or replacing unrelated settings.

## **2. Detailed configuration summary**

The table summarizes YAML settings to review when upgrading from V4 to V5, including changes, applicable versions and update instructions. Apply only the changes whose conditions match your deployment.

**Table conventions:** Configuration Key (V5) contains only the target property. For a removed declaration with no verified replacement, `—` indicates that no replacement key is specified; the V4 key remains in the before/after column. Where a verified alternative exists, it is listed explicitly. The applicable-version column lists the versions covered by this guide, rather than assuming that later branches inherit every change.

**Required** describes whether an upgrade action is needed, not whether a key was renamed:

- **Conditional:** update only if Update Condition matches and the target V5 profile/configuration does not already meet that requirement. This includes incompatible overrides, actual database settings, HA/AI, and required monitoring behavior. A renamed key with a suitable bundled value does not require a new declaration.
- **Yes (review):** review workflow retention before first startup because bundled dev/prod profiles enable cleanup. Retain the value if appropriate; change it only when cleanup is not permitted. This is a required review, not an unconditional value change.
- **No:** no mandatory change solely for the upgrade is identified. Keep suitable values. Optional tuning, internal help URLs, and recommended legacy cleanup remain documented; existing valid environment-specific settings must still be preserved.

No row requires a value change in every deployment simply because its key or sample value changed. Read the active profile and external overrides together: base YAML values can be overridden by dev/prod files, environment variables, or service options.

For legacy declarations, follow the listed migration action to match the target YAML; this classification does not claim that every old key causes startup failure. Optional values become relevant when operations require different behavior. For grouped rows, read each referenced configuration's condition rather than applying every setting unconditionally.

## **4. AI configuration for v5.1.0.0 and v5.1.0.1**

If AI is not used, retain `ai-service.enabled=false`; HMAC credentials are not required. If AI is used, prepare the following values before enabling the feature.

| Configuration key | Required | Requirement when enabling AI | Value to supply |
| --- | --- | --- | --- |
| `ai-service.enabled` | Conditional | Must be enabled | `true`, after URLs and HMAC credentials have been supplied. |
| `ai-service.frontend-url` | Conditional | URL must be confirmed | An http(s) URL users' browsers can access to open the AI UI. |
| `ai-service.backend-url` | Conditional | URL must be confirmed | An AI backend address reachable from Center; it may differ from the browser-facing URL. |
| `ai-service.hmac-key-id` | Conditional | Required | The key ID Center uses to sign lifecycle webhooks; the AI side must recognize this ID. |
| `ai-service.hmac-secret` | Conditional | Required | The lifecycle webhook signing secret, agreed between Center and the receiving AI system. |
| `ai-service.internal-auth.key-id` | Conditional | Required | The key ID AI uses to sign requests to Center. |
| `ai-service.internal-auth.hmac-secret` | Conditional | Required | The AI request authentication secret, agreed with the receiving Center system. |
| `ai-service.webhook-path` | Conditional | Change only if the backend uses a different path | Retain `/api/v1/center-lifecycle-events` if AI receives webhooks at this path. |
| `ai-service.internal-auth.allowed-clock-skew-seconds` | No | The supplied value can be retained | 60 seconds; synchronize the Center and AI clocks. |
| `ai-service.dispatcher-max-attempts`<br />`ai-service.dispatcher-retry-seconds` | No | The supplied values can be retained | 10 attempts and a 5-second retry delay; adjust only if operations require different values. |

**For production configuration:** replace sample HMAC values with credentials agreed with the AI system. The production YAML placeholders for `ai-service.hmac-key-id` and `ai-service.hmac-secret` contain an extra `}`; explicitly supply these two property values and verify HMAC requests in both directions before use. Do not use the development sample secrets.

The gateway references `ai-service.backend-url` even when `ai-service.enabled=false`. When using a custom profile, ensure backend-url has a valid value; the enabled flag does not automatically remove AI routes from the gateway configuration.

## **5. Configuration Examples**

These fragments show the V5 syntax. Merge them into the configuration loaded by the active profile, preserving unrelated settings and avoiding duplicate YAML keys.

### **5.1. Naming Strategy, JSON, Encoding, and Uploads**

Retain the environment's database settings. The following fragment illustrates the updated naming-strategy class and JSON/servlet property namespaces. Adjust the upload limits if the environment requires different values.

```yaml
spring:
  jpa:
    hibernate:
      naming:
        implicit-strategy: org.springframework.boot.hibernate.SpringImplicitNamingStrategy
  jackson:
    use-jackson2-defaults: true
    datatype:
      datetime:
        WRITE_DATES_AS_TIMESTAMPS: false
  servlet:
    encoding:
      charset: utf-8
      force-response: true
    multipart:
      enabled: true
      max-file-size: 200MB
      max-request-size: 200MB
```

### **5.2. Disable Workflow Cleanup Before First Startup**

The bundled V5 development and production profiles enable workflow retention. If cleanup is not yet permitted, set the following value before starting Center. This prevents cleanup even if the Quartz job remains stored in the database.

```yaml
retention:
  workflow:
    enable: false
```

Before enabling cleanup, review the saved retention policy of each workflow. The default-days, default-states, and default-log-only properties only prefill the form; changing them does not update saved policies.

### **5.3. AI URLs and HMAC Placeholder Correction**

For an AI-enabled 5.1.0.0 or 5.1.0.1 deployment, supply all environment variables below and merge this fragment into the loaded configuration. The correctly formed HMAC placeholders avoid the extra closing brace described in the production template. Use credentials agreed with the AI system rather than development sample secrets.

```yaml
ai-service:
  enabled: ${AI_SERVICE_ENABLED:false}
  frontend-url: ${AI_SERVICE_FRONTEND_URL}
  backend-url: ${AI_SERVICE_BACKEND_URL}
  hmac-key-id: ${AI_SERVICE_HMAC_KEY_ID}
  hmac-secret: ${AI_SERVICE_HMAC_SECRET}
  internal-auth:
    key-id: ${CENTER_INTERNAL_HMAC_KEY_ID}
    hmac-secret: ${CENTER_INTERNAL_HMAC_SECRET}
```

Verify signed requests in both directions before use. This fragment does not replace the target V5 gateway route list or CSP settings; apply those as described in Section 4 and the configuration tables.
